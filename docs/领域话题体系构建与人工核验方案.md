# 领域话题体系构建与人工核验方案

## 1. 目标

本流程利用已有的文档、章节和段落语料，自动生成一套有文本证据、可追溯、待人工核验的领域话题体系。

自动处理的定位是“发现候选”，不是替代领域专家制定正式标准。规则、机器学习聚类和大模型输出均不得未经审核直接发布。

## 2. 体系结构原则

领域体系由四部分组成：

1. **主分类树**：按技术对象或产业对象组织，回答“内容主要讲什么”。
2. **知识维度标签**：政策法规、产业市场、安全、标准、制造、运维等，回答“从什么角度讲”。
3. **术语体系**：记录规范名、别名、英文名、上下位关系和相关关系。
4. **文献属性**：来源类型、来源机构、时间、地区和权威等级。

主分类和知识维度不能混为同一棵树。例如“动力电池”是对象类，“政策法规”是知识维度；“动力电池回收管理办法”应标注为：

- 主分类：新能源汽车 → 动力电池 → 动力电池回收与梯次利用
- 知识维度：政策法规、回收与循环利用

## 3. 分析和标注粒度

章节是主要分析单元，段落用于细化，文档用于汇总。

原因是政策、白皮书和教材通常同时覆盖多个主题。如果只在文档层标一个类别，会把“风电、光伏、储能、动力电池、产业政策”等不同内容压缩成模糊的“新能源及新能源汽车”。

推荐的数据关系为：

```text
句子 → 段落 → 章节 → 文档
          细粒度证据   主标注    标签聚合
```

## 4. 自动处理流程

### 4.1 标题清理

标题识别在语料清洗阶段完成，采用“格式命中＋正文特征否决”的保守策略。日期时间、纯数字/表格行、目录点线、长法律条款、以句号结束的完整陈述句，以及过长的编号正文不得进入标题体系。每个有效标题记录识别规则和置信度。

话题构建程序随后清理已识别标题中的：

- 目录点线和页码；
- “第一章”“一、”“1.1”等编号；
- 纯页码、纯数字和图表残片；
- 多余空格和抽取符号。

所有原始标题、清理结果和质量标记都写入 `heading_cleaning_audit.csv`，便于抽样检查。程序不会修改原始语料。

### 4.2 种子话题匹配

`configs/topic_taxonomy_config.json` 保存可版本化的种子体系和关键词。

章节标题中的关键词权重高于正文；程序为每个章节保存：

- 候选话题；
- 匹配分数；
- 触发该判断的证据词；
- 候选知识维度。

种子匹配是可解释的基线，也是聚类结果命名的参考。

### 4.3 TF-IDF 和章节聚类

程序默认不依赖第三方包，使用标准库实现：

- 中文二至四字字符特征；
- 已知领域术语特征；
- 英文缩写和技术代码特征；
- 标题短语特征；
- TF-IDF 加权；
- 余弦相似度球面 K-means 聚类。

聚类用于发现：

- 种子体系遗漏的新话题；
- 应当拆分的混合类别；
- 可能合并的近义类别；
- 当前语料覆盖不足的类别。

聚类不等于正式分类。聚类可能同时受到文体、来源和主题影响，所以必须结合代表章节审核。

### 4.4 候选话题总结

每个聚类输出：

- 建议名称和建议父节点；
- 包含章节数、文档数；
- 关键词；
- 高频章节标题；
- 最有代表性的章节及正文摘录；
- 种子话题分布；
- 是否可能为混合簇。

这些信息进入 `candidate_taxonomy.json`、综合审核表 `topic_review_queue.csv` 和机器簇专项审核表 `cluster_review_queue.csv`。

`candidate_taxonomy.json` 同时包含两个质量和用途不同的层次：

1. `controlled_seed_nodes`：人工配置、可版本化的受控种子分类树；
2. `candidate_clusters`：由当前语料通过 TF-IDF 和球面 K-means 自动发现的候选簇。

机器聚类会受到文体、来源、重复章节名称和样本分布影响，其质量不应与受控种子节点等同。旧版 `topic_review_queue.csv` 只展开了第二层，同时压缩了 JSON 中的证据字段，因此会显得明显低于 JSON 中种子树的质量。新版综合审核表通过 `row_type` 同时列出两层，并为发现簇补充代表正文摘录、种子话题分布、质量标记和推荐动作。

### 4.5 可选大模型增强

显式使用 `--use-llm` 后，程序把聚类的关键词、标题和代表章节发送给兼容 OpenAI Chat Completions 的接口，让模型建议：

- 更简洁的话题名称；
- 父节点；
- 定义；
- 纳入与排除范围；
- 是否需要拆分；
- 是否应与其他簇合并；
- 置信度和理由。

安全和治理规则：

- API key 只从环境变量 `TOPIC_LLM_API_KEY` 读取；
- 程序不打印、不保存 key；
- 仅发送聚类摘要和有限正文摘录；
- 大模型建议写入单独字段，不覆盖规则结果；
- `review_status` 始终保持“待人工核验”；
- 如果语料涉密或不允许外发，不得启用外部大模型，可改接机构内部兼容接口。

## 5. 输出文件

默认输出目录：

```text
D:\production\corpus\processed\taxonomy_candidates
```

| 文件 | 用途 |
|---|---|
| `candidate_taxonomy.json` | 完整种子树、候选聚类、证据和可选大模型建议 |
| `section_topic_candidates.jsonl` | 每个章节的候选主分类、知识维度、聚类和置信信息 |
| `topic_review_queue.csv` | 受控种子节点与机器发现簇的综合审核表，使用 `row_type` 区分 |
| `cluster_review_queue.csv` | 仅包含机器发现簇的专项审核表 |
| `term_review_queue.csv` | 术语频次、文档覆盖、所属种子节点及规范化审核栏 |
| `heading_cleaning_audit.csv` | 标题清理前后对照和质量标记 |
| `run_report.json` | 输入、参数、数量、模型使用情况和错误摘要 |

CSV 使用 UTF-8 with BOM，便于直接用 Excel 打开。

## 6. 运行方法

### 6.1 默认运行：规则和机器学习

```powershell
powershell -ExecutionPolicy Bypass -File D:\production\corpus\scripts\run_topic_taxonomy.ps1
```

也可以指定可工作的 Python：

```powershell
$env:CORPUS_PYTHON = 'C:\path\to\python.exe'
powershell -ExecutionPolicy Bypass -File D:\production\corpus\scripts\run_topic_taxonomy.ps1
```

直接运行 Python：

```powershell
python D:\production\corpus\scripts\build_topic_taxonomy.py `
  --input-root D:\production\corpus\processed\jsonl `
  --output-root D:\production\corpus\processed\taxonomy_candidates `
  --config D:\production\corpus\configs\topic_taxonomy_config.json `
  --clusters 24
```

### 6.2 启用大模型

```powershell
$env:TOPIC_LLM_API_KEY = '在本机安全设置，不要写入代码或配置'
$env:TOPIC_LLM_MODEL = '机构批准使用的模型名'
$env:TOPIC_LLM_BASE_URL = 'https://api.openai.com/v1'

powershell -ExecutionPolicy Bypass `
  -File D:\production\corpus\scripts\run_topic_taxonomy.ps1 `
  -UseLlm
```

如果使用机构内部兼容接口，只需调整 `TOPIC_LLM_BASE_URL`、模型名和密钥。

## 7. 人工核验流程

审核人员先打开 `topic_review_queue.csv` 核验受控种子节点的定义、纳入范围、排除范围和父子关系，再打开 `cluster_review_queue.csv` 逐簇查看：

1. 代表标题和关键词是否表达同一技术对象；
2. 代表章节是否语义一致；
3. 建议名称是否采用行业规范术语；
4. 建议父节点是否属于相同划分维度；
5. 是否需要拆分或与其他簇合并；
6. “政策、市场、安全、标准”等是否误放进主分类树；
7. 是否有足够语料支撑一个独立三级类别。

在以下字段填写人工决定：

- `human_decision`：通过、改名、改父节点、拆分、合并、拒绝；
- `approved_label`：正式名称；
- `approved_parent_id`：正式父节点；
- `reviewer`：审核人；
- `review_notes`：定义、边界和理由。

建议至少由一名语料工程人员和一名领域专家审核。容易混淆的关键类别可采用双人独立审核。

## 8. 验收标准

V0.1 体系建议达到：

- 90% 以上有效章节能够进入主分类候选；
- “其他、综合、待定”不超过 15%；
- 每个正式三级类原则上至少有 3 个有效章节；
- 每个类别都有定义、纳入范围、排除范围和代表证据；
- 人工抽样标注一致率达到 80% 以上；
- 自动结果保存方法、参数、版本和证据；
- 新语料只能提出新增或修改候选，不能自动改变正式体系。

## 9. 版本管理

正式发布时应将：

- 配置中的 `taxonomy_version` 从 `0.1-draft` 更新为正式版本；
- 审核后的体系另存为正式文件，不覆盖机器生成的候选文件；
- 保存变更日志，记录新增、拆分、合并、改名和废弃节点；
- 在章节标注中记录所用体系版本。

推荐版本：

```text
0.1-draft     自动生成的首轮候选
0.1-review1   第一轮人工核验
1.0           首个正式发布版本
1.1           增量扩展或小范围调整
2.0           分类原则或一级结构发生重大变化
```
