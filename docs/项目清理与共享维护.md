# 项目清理与共享维护

## 本次范围

按所有者要求删除旧单用户原始语料、加工中间结果、正式成果副本、历史轮次、测试资产、旧源码生成脚本及过时阶段和研究文档。现有账号与 `data/portal/` 下用户项目保留；`.env` 和数据库密码不进入共享包。

保留当前程序、回归测试、配置、必要词表接口、分词组件、许可证、上传模板和当前操作及部署指南。PostgreSQL 中旧主项目历史记录与文件保持一致，用户项目 schema 和账号表独立保留。

## 三个共享成果

`deliveries/2026-10-09/01-builder/`：当前多用户构建程序、干净项目模板、维护测试与核心便携环境。下载者需自行准备 PostgreSQL、话题依赖、模型缓存和实际句法服务。

`02-corpus-data/`：空的正式版本导出容器及操作说明。原历史成果按要求删除，之后从用户项目导出自己有权分享的完整 Release。

`03-search-service/`：只读检索程序、空的 releases 目录和核心便携环境。导入完整成果后运行。无需账号与数据库；共享主平台的用户版本则优先在第 6 步生成授权链接。

每部分有独立 README，外层提供 ZIP、SHA256SUMS.txt 和发行清单。发行包不带个人原文、真实 .env、账号记录、密钥、Git 历史及测试产物。原便携核心环境沿用，BERTopic 依赖和模型仍需首次安装；不是全环境离线镜像。

## 后续维护

修改当前源码后，用 `scripts/maintenance/build_share_packages.py` 在新输出目录生成发行包，再运行目录和 ZIP 检查。工具拒绝覆盖已有目录；只有核对后才替换共享目录。不要把运行中的用户目录直接打包发布。模板更新只影响新项目；已有项目程序升级应先结束任务并备份，保留其配置和数据。

缓存可重建。原文和正式 Release 不应在日常维护中默认删除，本次删除是所有者明确授权的集中清理。用户项目需要删除时，应同时处理项目记录、分享授权和对应资产，不能只删文件夹。

GitHub 同步当前完整源码与新版发行包；以后本机重新打包后仍需单独上传 GitHub。
